If a New-Architecture interop issue surfaces at build, fall back to `expo-secure-store` (documented in research §6.2) and note the swap; otherwise proceed with react-native-keychain.
2. Create `app/src/services/secureTokenStore.ts` — a thin wrapper exposing the same get/set/remove shape AsyncStorage offered, backed by keychain:
   - `setTokens(tokens)` -> `Keychain.setGenericPassword('risevpn-auth', JSON.stringify(tokens), { service: 'risevpn.auth' })`
   - `getTokens()` -> `Keychain.getGenericPassword({ service: 'risevpn.auth' })` -> parse JSON or null
   - `clearTokens()` -> `Keychain.resetGenericPassword({ service: 'risevpn.auth' })`
   Use the same `service` key consistently (this is the Keychain entry SC#5 inspects).
3. In `authStore.ts`, swap ALL 7 AsyncStorage token sites to `secureTokenStore` (initialize read+write, linkWithCode, signInWithApple, signInWithGoogle, updateTokens, logout). Tokens never touch AsyncStorage again.
4. D-12 wipe (force-re-login + implicit wipe): on app boot (`initialize`), add a one-time `AsyncStorage.removeItem('auth-tokens')` so users upgrading in place end with no token in AsyncStorage (satisfies the D-12 literal lock). Because 08-04 cleared sessions server-side, any carried-forward token is already dead -> the app routes to login; the fresh tokens from that login are written straight to Keychain. Do NOT migrate-then-carry-forward (the token is dead — research §6.4).
5. HARD-04 client side: in the api.ts refresh interceptor, include `device_id` (from `getDeviceFingerprint()`) in the `/auth/refresh` request body so the backend can hard-check it.
  </action>
