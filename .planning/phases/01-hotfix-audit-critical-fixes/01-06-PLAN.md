<objective>
Land HOTFIX-05: wrap the refresh-token rotation in `handler/auth.go:241-263` inside a single `db.Transaction(func(tx *gorm.DB) error { ... })` closure. Today the sequence is `DeleteSession(db, session.ID)` (return ignored) → `FindUserByID(db, …)` → `generateTokens(...)` → `storeRefreshSession(db, …)` (failure only logged) — so if storeRefreshSession fails, the client receives valid tokens whose refresh half has no DB row and gets silently logged out on the next refresh. The fix performs all four steps inside one transaction; any error rolls back the delete, preserving the old session row. Per RESEARCH §HOTFIX-05 "Notice", reuse `storeRefreshSession(tx, …)` (the helper already accepts any `*gorm.DB`).

Purpose: closes SECURITY-AUDIT S1-1. Implements ROADMAP §Phase 1 success criterion #7.

<threat_model>
  <threat id="T-1-05" severity="high" category="Tampering">
    <description>The current refresh-rotation sequence in handler/auth.go:241-263 deletes the old session row, then mints new tokens, then attempts to insert the new session row. If the insert fails (transient DB error, future UNIQUE constraint collision after HOTFIX-07), the failure is logged but the response still returns the new tokens to the client. The client's refresh token is now valid-looking but unbacked by any DB row — the next refresh call will 401, silently logging the user out. Result: silent session loss / token tampering from any transient DB blip.</description>
    <mitigation>Task 2 wraps DeleteSession + FindUserByID + generateTokens + storeRefreshSession inside a single `db.Transaction(func(tx *gorm.DB) error)` closure. Any error returned from the closure rolls back the BEGIN/COMMIT — the original session row stays in place and the user can refresh again later. The closure assigns the generated tokens to an outer variable only after the insert succeeds, so the HTTP response carries tokens only when the new session row is committed. User-not-found errors are distinguished from other DB errors so the client gets the correct status (401 vs 500).</mitigation>
    <verification>Acceptance criteria in Task 2: integration test `TestRefreshToken_RollbackOnInsertFailure` using sqlite — pre-insert a row with the same hash to trigger a UNIQUE collision (or use a callback that errors), assert the old session row STILL EXISTS after the failed rotation, and the HTTP response is 500. Smoke from plan 09 step 6 verifies on staging.</verification>
  </threat>
