<threat_model>
  <threat id="T-1-03" severity="high" category="Denial of Service">
    <description>The current IncrRateLimit does INCR and EXPIRE as separate Redis round-trips. If Redis (or the network to Redis) hiccups between the two, the counter is incremented but never gets a TTL. The counter then persists forever, leaving any legitimate user from that IP permanently rate-limited (self-DoS) until manual operator intervention deletes the key. Even more concerning: under partial Redis restart scenarios the EXPIRE can succeed against a key that no longer carries the increment, also producing inconsistent state.</description>
    <mitigation>Task 2 replaces the two-round-trip pipeline with a single Lua EVAL script that atomically runs INCR-then-conditionally-EXPIRE inside Redis's single-threaded script engine. Either both operations happen or neither does — partial state is structurally impossible. Implemented via `redis.NewScript(src).Run(ctx, client, keys, args)`, which transparently uses EVALSHA after the first call so there's no per-call script-upload cost.</mitigation>
    <verification>Acceptance criteria in Task 2: `cd server/api && go test ./internal/cache/... -v -run TestIncrRateLimit` PASSes. Tests assert: (1) TTL > 0 after first increment; (2) TTL still > 0 after subsequent increments (no sliding-window regression); (3) miniredis FastForward past window expires the key, next increment starts at 1; (4) round-trip-count invariant: only one EVAL/EVALSHA per call. Smoke from plan 09 step 5 verifies on staging.</verification>
  </threat>
</threat_model>
