WithUserLock pattern (RESEARCH §8.1, adapted to db.WithContext(ctx)):
  func WithUserLock(ctx context.Context, db *gorm.DB, userID string, fn func(tx *gorm.DB) error) error {
      return db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
          if err := tx.Exec("SELECT pg_advisory_xact_lock(hashtextextended(?, 0))", userID).Error; err != nil {
              return err
          }
          return fn(tx) // all subscription/user/audit writes happen on tx, inside the lock
      })
  }
hashtextextended maps the UUID string → bigint; _xact_lock auto-releases on COMMIT/ROLLBACK (crash-safe, no unlock bookkeeping). NOTE: pg_advisory_xact_lock does NOT exist in SQLite — the race test MUST use testutil.StartPostgres (real Postgres). WithUserLock must degrade gracefully on non-Postgres dialects ONLY in tests that don't exercise it; production is always Postgres.

webhook_lava.go (internal/handler/webhook_lava.go) tier-grant paths:
  - handleLavaPaymentSuccess(ctx, logger, db, redis, event): resolves inv.UserID, then SetUserPlan + UpsertLavaContract + UpdateInvoiceStatus + BustUserCache.
  - handleLavaRecurringSuccess(ctx, logger, db, redis, event): resolves parent.UserID, then SetUserPlan + UpsertLavaContract + update parent + BustUserCache.
  The user_id is resolved BEFORE the writes in both. Wrap the WRITE block (SetUserPlan onward) in repository.WithUserLock(ctx, db, userID, func(tx) error { ... use tx instead of db ... }). The InsertWebhookEventIfNew dedup INSERT stays OUTSIDE/BEFORE the lock (it must commit independently — see webhook_event_repo.go comment; do NOT move it inside the lock transaction). BustUserCache stays AFTER the lock commits (it's a Redis side-effect, not part of the DB transaction).
  CRITICAL: SetUserPlan currently opens its OWN db.WithContext(ctx).Transaction. Inside WithUserLock you already hold a tx — call the write logic on `tx` directly, NOT via SetUserPlan(db,...) which would open a nested/second transaction outside the lock. Either (a) add a SetUserPlanTx(tx, ...) variant that takes the *gorm.DB tx and does the same writes without opening its own Transaction, and have SetUserPlan call it, OR (b) inline the user/subscription/contract writes onto tx within the webhook closure. Prefer (a): refactor SetUserPlan to delegate to SetUserPlanTx(tx, ...) — cleaner and reusable by force-cancel.

force-cancel handler (NEW, in admin_user_controls.go from 07-04):
  AdminCancelSubscription(logger, db, redisClient) — body {refund bool, reason string}. Inside WithUserLock(ctx, db, userID, func(tx) error):
    1. Re-read user/contract state ON tx (so it sees the latest committed value, serialized against the webhook).
    2. If already cancelled → return a sentinel so the handler responds 409 (no double-cancel).
    3. Reset the user to the system (free) plan via the tx writes (mirror SetUserPlanTx with the system plan id + nil expiresAt), set lava_contracts.is_active=false + cancelled_at=now() for the user's active contract.
    4. Write CreateAuditEntry (on tx) Action="cancel_subscription" Details{"reason":reason, "refund_intent":refund}. refund=true records ONLY intent (no lava call — A3).
  After the lock commits: BustUserCache best-effort. Return 200 {data:{subscription_id, cancelled_at, refund_status:"intent_recorded"|"none"}}.

cmd/main.go admin group: add admin.Post("/users/:id/cancel-subscription", handler.AdminCancelSubscription(logger, db, redisClient)). audit.go describeAction: add case for cancel_subscription.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| admin force-cancel ⟷ lava webhook | two independent writers racing on one user's subscription state |
| handler → Postgres advisory lock | transaction-scoped lock acquisition |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-18 | Tampering | concurrent force-cancel + payment.success → hybrid state | mitigate | both paths take pg_advisory_xact_lock(hashtextextended(user_id,0)) on the SAME key inside their transaction — mutual exclusion serializes them; proven by TestForceCancelWebhookRace |
| T-07-19 | Tampering | webhook replay/duplicate → double grant | mitigate | lava_webhook_events UNIQUE dedup (unchanged) + set-not-increment tier grant; the advisory lock is ADDITIONAL, not a replacement |
| T-07-20 | DoS | advisory-lock exhaustion | mitigate | xact-scoped locks auto-release on commit/rollback (no leaked locks); transaction bodies are tight (a few row writes); single user key cannot exhaust the shared pool |
| T-07-21 | Spoofing | force-cancel keyed on wrong identity vs webhook | mitigate | BOTH lock on the resolved user_id (webhook resolves inv.UserID/parent.UserID before locking) — Pitfall 1 closed; the race test fails if keys diverge |
| T-07-22 | Business Logic | lava refund executed without capability | mitigate | A3 — force-cancel records refund INTENT only; no lava refund method is called (none exists) |
</threat_model>
