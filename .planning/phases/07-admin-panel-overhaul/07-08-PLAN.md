<objective>
Implement ADMIN-06: the webhook event log + replay. Refactor the existing webhook_lava.go event dispatch into a reusable, transport-free applyLavaEvent function. The live handler calls it; the new POST /admin/webhook-events/:id/replay re-calls it with the STORED payload row. Replay is idempotent because the tier grant is set-not-increment (re-applying yields the same state, never a double grant). Replay flips the row status DELIVERED→REPLAYED, bumps retried_count, and MUST take the same WithUserLock(user_id) as the live path so a replay racing a live webhook does not reopen the ADMIN-03 race. The replay-idempotency integration test (TestWebhookReplayIdempotent, RED from 07-01) is the load-bearing proof.

Per A1 (LOCKED): use the EXISTING lava_webhook_events table — do NOT create a generic webhook_events table. The status column was added in migration 024.

Purpose: ADMIN-06 success criterion — admin clicks Replay on a DELIVERED event → side effect re-applied idempotently, status flips to REPLAYED.
Output: applyLavaEvent extraction, Status/RetriedCount model fields, list + replay endpoints, email redaction in the list, GREEN replay test.
</objective>
